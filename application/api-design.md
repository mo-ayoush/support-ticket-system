# API Design

## 1. Overview

The Support Ticket Management System provides a REST API for creating, retrieving, listing, updating, and deleting support tickets.

The API uses the following AWS architecture:

`Client -> API Gateway -> AWS Lambda (Python) -> DynamoDB`

### Component Responsibilities

- **Client:** Sends HTTP requests and receives HTTP responses.
- **API Gateway:** Exposes HTTP endpoints, handles HTTP methods, and forwards requests to the appropriate Lambda integration.
- **AWS Lambda (Python):** Implements business logic, validates input, performs CRUD operations, and generates HTTP responses and error messages.
- **DynamoDB:** Stores ticket data persistently.

## 2. Base Path

`/tickets`

## 3. Endpoints

| Method | Path | Description |
|---|---|---|
| POST | `/tickets` | Create a new ticket |
| GET | `/tickets` | List all tickets |
| GET | `/tickets/{ticket_id}` | Retrieve a ticket by ID |
| PUT | `/tickets/{ticket_id}` | Replace the mutable fields of an existing ticket |
| DELETE | `/tickets/{ticket_id}` | Delete an existing ticket |

## 4. Ticket Data Model

Each ticket contains the following attributes:

| Attribute | Type | Description |
|---|---|---|
| ticket_id | String | Unique ticket identifier, generated by the application |
| title | String | Short ticket title |
| description | String | Detailed description of the issue |
| priority | String | LOW, MEDIUM, HIGH, or CRITICAL |
| status | String | OPEN, IN_PROGRESS, or RESOLVED |
| created_by | String | Name or identifier of the ticket creator |
| created_timestamp | String | Creation timestamp in UTC |
| updated_timestamp | String | Last update timestamp in UTC |

### Example Ticket

```json
{
  "ticket_id": "ticket-123",
  "title": "Cannot access company email",
  "description": "The user cannot log in to the company email account.",
  "priority": "HIGH",
  "status": "OPEN",
  "created_by": "employee@example.com",
  "created_timestamp": "2026-11-06T12:00:00Z",
  "updated_timestamp": "2026-11-06T12:00:00Z"
}
```

## 5. Request and Response Examples

### 5.1 Create a Ticket

**Request**

`POST /tickets`

```json
{
  "title": "Cannot access company email",
  "description": "The user cannot log in to the company email account.",
  "priority": "HIGH",
  "created_by": "employee@example.com"
}
```

The application generates the following fields:

- `ticket_id`
- `created_timestamp`
- `updated_timestamp`

If the status is not provided, it defaults to `OPEN`.

**Successful Response: HTTP 201 Created**

Returns the newly created ticket, including its generated ID and timestamps.

### 5.2 List All Tickets

**Request**

`GET /tickets`

**Successful Response: HTTP 200 OK**

```json
{
  "tickets": [
    {
      "ticket_id": "ticket-123",
      "title": "Cannot access company email",
      "description": "The user cannot log in to the company email account.",
      "priority": "HIGH",
      "status": "OPEN",
      "created_by": "employee@example.com",
      "created_timestamp": "2026-11-06T12:00:00Z",
      "updated_timestamp": "2026-11-06T12:00:00Z"
    }
  ]
}
```

### 5.3 Retrieve a Ticket by ID

**Request**

`GET /tickets/ticket-123`

**Successful Response: HTTP 200 OK**

Returns the requested ticket as a JSON object.

If the ticket does not exist, the API returns `404 Not Found`.

### 5.4 Update a Ticket

**Request**

`PUT /tickets/ticket-123`

PUT replaces all mutable ticket fields. The request must include all five fields:

```json
{
  "title": "Email access restored",
  "description": "The email login issue has been investigated.",
  "priority": "MEDIUM",
  "status": "IN_PROGRESS",
  "created_by": "employee@example.com"
}
```

The application:
- Validates all supplied fields.
- Updates the ticket attributes.
- Keeps the original `ticket_id` and `created_timestamp`.
- Refreshes `updated_timestamp`.

**Successful Response: HTTP 200 OK**

Returns the updated ticket.

If the ticket does not exist, the API returns `404 Not Found`.

### 5.5 Delete a Ticket

**Request**

`DELETE /tickets/ticket-123`

**Successful Response: HTTP 200 OK**

```json
{
  "message": "Ticket deleted successfully",
  "ticket_id": "ticket-123"
}
```

If the ticket does not exist, the API returns `404 Not Found`.

## 6. Validation Rules

The application validates incoming requests before performing database operations.

### Required Fields for Creation

- `title`
- `description`
- `priority`
- `created_by`

The `status` field is optional during creation and defaults to `OPEN`.

### Allowed Values

**Priority:**
- LOW
- MEDIUM
- HIGH
- CRITICAL

**Status:**
- OPEN
- IN_PROGRESS
- RESOLVED

### Additional Rules

- Required string fields must not be empty or contain only whitespace.
- `priority` must match one of the allowed values.
- `status`, when supplied, must match one of the allowed values.
- The application generates a unique `ticket_id`.
- Timestamps are generated in UTC.
- The client cannot overwrite the generated ID or creation timestamp.
- PUT requests must contain all mutable fields.
- Updating or deleting a non-existing ticket returns HTTP 404.

## 7. DynamoDB Operation Mapping

Lambda uses the AWS SDK for Python (Boto3) to communicate with DynamoDB.

| API Endpoint | DynamoDB Operation | Purpose |
|---|---|---|
| POST `/tickets` | PutItem | Store a new ticket |
| GET `/tickets` | Scan | Retrieve all tickets |
| GET `/tickets/{ticket_id}` | GetItem | Retrieve one ticket by its partition key |
| PUT `/tickets/{ticket_id}` | UpdateItem | Update an existing ticket |
| DELETE `/tickets/{ticket_id}` | DeleteItem | Delete a ticket |

### DynamoDB Design

- Each ticket is stored as one DynamoDB item.
- `ticket_id` is the partition key.
- No sort key is required for the initial project scope.

**Note about Scan:** Scan is acceptable for this small educational project. It reads across the table and can become inefficient and costly as the number of tickets grows. Pagination, Query operations, or additional indexes can be considered in a future version.

## 8. HTTP Status Codes

| Status Code | Meaning | When It Is Used |
|---|---|---|
| 200 | OK | Successful retrieval, update, or deletion |
| 201 | Created | Ticket successfully created |
| 400 | Bad Request | Missing required fields or invalid input |
| 404 | Not Found | Requested ticket does not exist |
| 500 | Internal Server Error | Unexpected server-side failure |

HTTP 401 Unauthorized may be introduced when authentication is implemented. It is not part of the initial implemented API contract.

### Example Error Responses

**HTTP 400 Bad Request**

```json
{
  "error": "Invalid priority. Allowed values: LOW, MEDIUM, HIGH, CRITICAL."
}
```

**HTTP 404 Not Found**

```json
{
  "error": "Ticket not found",
  "ticket_id": "ticket-999"
}
```

**HTTP 500 Internal Server Error**

```json
{
  "error": "An internal server error occurred."
}
```

Unexpected internal exception details should be logged for troubleshooting, not exposed to API clients.

## 9. Error Handling and Logging

The Lambda function is responsible for:

- Validating request data.
- Returning meaningful error messages.
- Handling missing tickets.
- Handling unexpected database or application errors.
- Logging relevant events and errors to Amazon CloudWatch.

Error responses should use consistent JSON structures.

Sensitive information and internal exception details must not be returned to clients.

## 10. Security Considerations

- Lambda accesses DynamoDB through an IAM execution role.
- IAM permissions follow the principle of least privilege.
- The Lambda role should only have the required DynamoDB actions on the project table.
- CloudWatch logging permissions are required for application logs.
- AWS credentials must not be hardcoded in the source code or committed to GitHub.
- Authentication and authorization for API clients are not yet implemented and must be considered before using the API with sensitive or production data.

## 11. Initial API Behavior

- New tickets default to status `OPEN` when no status is supplied.
- New tickets receive a unique ID.
- Creation and update timestamps use UTC.
- Updating a ticket refreshes `updated_timestamp`.
- The original `created_timestamp` remains unchanged.
- Missing tickets return HTTP 404.
- Invalid request data returns HTTP 400.
- Unexpected errors return HTTP 500.
