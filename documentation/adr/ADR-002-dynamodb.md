# ADR-002: Selection of Amazon DynamoDB

## Status

Accepted

## Date

2026-11-06

## Context

The Support Ticket Management System needs persistent storage for support tickets and related operational records.

Each ticket contains business attributes such as:

- `ticket_id`
- `title`
- `description`
- `priority`
- `status`
- `created_by`
- `created_at`
- `updated_at`

The implementation also uses additional attributes to support querying, concurrency control, and administrative access:

- `version`
- `admin_partition`
- `created_sort`

The application must support creating, listing, retrieving, updating, and deleting tickets. It must also track write operations, maintain audit history, and manage notification delivery.

Two database services were considered: Amazon DynamoDB and Amazon RDS.

## Decision

Amazon DynamoDB was selected as the database service.

DynamoDB provides a managed NoSQL database that integrates directly with AWS Lambda and supports the access patterns required by the application.

The implementation uses four DynamoDB tables to separate ticket data from operational records.

## DynamoDB Data Model

DynamoDB is a NoSQL database.

- Data is stored in tables.
- Each table contains items.
- Each item contains attributes.
- Items do not require a fixed relational schema.
- Primary keys identify items and support efficient access patterns.

The Tickets table stores each support ticket as an individual item. The `ticket_id` attribute is the partition key.

Example ticket item:

```json
{
  "ticket_id": "TICKET-001",
  "title": "Login problem",
  "description": "Unable to log in",
  "priority": "HIGH",
  "status": "OPEN",
  "created_by": "student",
  "created_at": "2026-11-06T10:00:00Z",
  "updated_at": "2026-11-06T10:00:00Z",
  "version": 1,
  "admin_partition": "ALL",
  "created_sort": "2026-11-06T10:00:00Z"
}
```

The example illustrates the logical ticket attributes; actual identifiers and timestamps are generated by the application.

### Supporting DynamoDB Tables

The implementation uses four DynamoDB tables:

| Table | Purpose |
|---|---|
| Tickets | Stores ticket details and supports user/admin ticket queries through secondary indexes. |
| Idempotency | Tracks write requests to prevent duplicate operations. Expired records are removed using TTL. |
| Audit | Stores ticket history and audit events. |
| Notifications | Stores notification outbox records and tracks their delivery status. |

Separating these records gives each table a clear responsibility and avoids mixing ticket data with operational processing state.

### Tickets Table and Secondary Indexes

The Tickets table uses `ticket_id` as its partition key.

It also has two Global Secondary Indexes:

- **UserTicketsIndex:** supports listing tickets by `created_by`, using `created_sort` for ordering.
- **AdminTicketsIndex:** supports administrative ticket listing through `admin_partition`, using `created_sort` for ordering.

These indexes support the application's user and administrative listing patterns without requiring a full table scan for those queries.

The `created_sort` attribute supports newest-first ticket listings.

### Notifications Table and Secondary Index

The Notifications table uses `NotificationStatusIndex` to find notification records by status and creation time.

This supports the scheduled Notification Worker when it searches for eligible pending notifications.

### Billing and Encryption

All four DynamoDB tables use:

- `PAY_PER_REQUEST` billing mode.
- Server-side encryption.

On-demand billing was selected because the project has a relatively small and unpredictable workload. It avoids the need to provision read and write capacity in advance.

Server-side encryption provides encryption at rest for stored table data.

## Data Consistency and Concurrency

### DynamoDB Transactions

The application uses DynamoDB transactions for related write operations.

A successful ticket write can involve multiple related records, including:

- The ticket record.
- The corresponding audit event.
- The idempotency operation completion record.
- The notification outbox record.

Using a transaction allows the related DynamoDB changes to succeed or fail together, helping prevent partially completed application operations.

### Optimistic Locking

The ticket model includes a `version` attribute.

The version is used for optimistic concurrency control during updates.

The application checks the expected version when applying an update. If another operation has already changed the ticket, the version no longer matches and the stale update can be rejected.

This helps prevent one user from silently overwriting another user's more recent changes.

### Idempotency

The Idempotency table tracks client write operations.

It helps the application recognize repeated requests and avoid processing the same logical operation more than once.

This is particularly important because write requests are accepted asynchronously and processed through SQS FIFO.

TTL is used to remove expired idempotency records after their configured lifetime.

### Audit History

The Audit table stores historical events associated with ticket operations.

This separates the current ticket state from its historical changes and supports audit-history queries.

### Notification Outbox

The Notifications table implements a durable notification outbox.

Notification intent is stored as part of the related DynamoDB transaction rather than relying on an immediate SNS publish during the ticket write.

A scheduled worker processes eligible pending records and publishes notifications through SNS.

The implementation distinguishes definite SNS service rejections from ambiguous outcomes. Definite rejections can be retried with a bounded attempt count, while ambiguous outcomes are quarantined to avoid automatic duplicate publication.

This design separates ticket persistence from external notification delivery.

## Ticket Lifecycle and Deletion

Ticket deletion is implemented as a soft delete.

Instead of physically removing the ticket item, the application updates its status to `DELETED`.

This preserves the ticket record and its historical information while allowing the application to treat it as deleted.

Soft deletion is useful for auditability and avoids losing historical ticket data through a normal delete operation.

## CRUD Operation Mapping

The application uses the following DynamoDB operations and access patterns:

| Application operation | DynamoDB operation or access pattern |
|---|---|
| Create ticket | `PutItem` within the relevant transaction |
| List tickets for a user | `Query` on `UserTicketsIndex` |
| List tickets for an administrator | `Query` on `AdminTicketsIndex` |
| Retrieve ticket by ID | `GetItem` |
| Update ticket | Conditional transactional update using the expected version |
| Delete ticket | Transactional update that changes the ticket status to `DELETED` |
| Track write operation | Idempotency table lookup and update |
| Retrieve audit history | Query against the Audit table's configured key access pattern |
| Find pending notifications | Query using `NotificationStatusIndex` |

Ticket lists use `created_by` with `created_sort` for user queries and `admin_partition` with `created_sort` for administrative queries.

Operation-status retrieval uses the operation identifier and applies actor, ticket-owner, or administrator authorization as appropriate.

## Alternatives Considered

### Option A – Amazon DynamoDB

Advantages:

- Managed NoSQL database without database server management.
- Suitable for key-based access using `ticket_id`.
- Integrates directly with AWS Lambda through the AWS SDK.
- Supports on-demand capacity mode.
- Supports secondary indexes for defined access patterns.
- Supports conditional writes and transactions.
- Fits the project's ticket CRUD and operational record requirements.

Disadvantages:

- Does not provide the same relational model and SQL join capabilities as RDS.
- Query patterns should be considered when designing tables and indexes.
- A Scan operation can become inefficient and costly as the table grows.
- Data modelling requires understanding partition keys, sort keys, and indexes.

### Option B – Amazon RDS

Amazon RDS is a managed relational database service.

Data is organized into tables, rows, and columns, and applications use SQL to query and modify data.

Advantages:

- Supports SQL queries.
- Supports relationships between tables and relational joins.
- Suitable for complex relational data models.
- Useful for reporting and queries that combine related entities.

Disadvantages:

- Requires database engine and connection configuration.
- Database capacity and connection management must be considered.
- Relational database access from Lambda requires attention to connection management.
- More than the project currently needs for its ticket-based access patterns.

## Consequences

### Positive Consequences

- Simple data model for individual support tickets.
- Direct access using the `ticket_id` partition key.
- Efficient user and administrative listing through secondary indexes.
- No relational joins are required for the current scope.
- Transactions support consistency across related application records.
- Version-based concurrency control helps prevent stale updates.
- Separate tables provide clear boundaries between tickets and operational records.
- Direct integration with the selected serverless architecture.
- On-demand billing avoids manual capacity provisioning.

### Negative Consequences

- Less suitable for complex relational queries.
- Future filtering and access patterns may require additional secondary indexes.
- Scan operations should not be relied on for large datasets.
- Transactional operations add application and implementation complexity.
- Incorrect partition-key or index design can affect query efficiency.
- Data relationships and reporting capabilities require more deliberate application-level design than in a relational database.

## Rationale

The current application primarily works with individual tickets identified by a unique `ticket_id`.

It does not require complex relational relationships or SQL joins for its core operations.

DynamoDB provides the required persistence, indexing, conditional updates, and transaction capabilities while integrating directly with the selected AWS serverless architecture.

The four-table design separates ticket data, idempotency tracking, audit history, and notification delivery state.

Amazon RDS remains a possible alternative if future requirements introduce complex relational data, SQL-based reporting, or extensive relationships between entities.
